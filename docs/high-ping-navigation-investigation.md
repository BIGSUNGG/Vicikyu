수치는 동일 테스트 이미지/시드에서의 단회 표본이며 실제 iPhone의 대기시간이라고 주장하지 않는다. 두 조건 모두:

1. 이름 공백·학번/학과 `·`, 가입일 `0001.01.01`이 나타난다.
2. 달력 제목 `0년 0월`, 이번 달/학기/전체 `0회`가 실제 데이터처럼 나타난다.
3. 통계 카드는 처음에 없다가 최종 데이터와 함께 삽입된다.
4. 그때 달력이 약 159px 아래로 이동한다. 측정된 것은 **본문 재배치**이며 하단 내비가 움직인다는 결론은 아니다.
5. 브라우저 pageerror는 0건이다. 최종 데이터/기능 정상과 로딩 중 표현 문제는 구분된다.

## 소스와 연결되는 확정 사실

`VolleyballClub.Client/Components/Pages/MyPage.razor`:

- 헤더가 nullable profile을 즉시 출력하고 가입일에 `DateTime.MinValue`를 대입한다.
- 달력은 `new(0, 0, [], 0, 0, 0)`인데 그 Year/Month/카운트를 조건 없이 출력한다.
- 통계 카드는 `semesterStats is not null`일 때만 추가된다.
- `OnInitializedAsync`가 profile → stats → calendar를 순차 await한다. 달력 요청에는 프로필/통계 응답이 필요하지 않고 선택 년/월만 필요하다.
- 해당 메서드에는 중간 `StateHasChanged`가 없다. 관측에서도 초기 미완성 프레임과 전체 로딩 후 프레임이 보이고, 3개 응답마다 화면이 각각 완성되는 패턴은 아니었다.

**현재 이미지에서 확인된 원인 조합:** 미로딩 상태를 정상 데이터/빈 완성 화면처럼 표시하는 초기 렌더 + 나중에 통계/달력 내용을 추가하는 재배치. 순차 API 호출이 그 미완성 화면의 노출 시간을 고지연에서 늘린다.

**실기기 사용자 확인이 필요한 연결:** 이것이 실제 iPhone에서 사용자가 거슬린다고 한 현상과 같은지, 임시 값/재배치/대기시간 중 어떤 것을 해결 대상으로 삼을지. 이 확인 전에는 개선 방향을 선택하지 않는다.

## 별도 관찰: 홈 로딩 중 바로 이동할 때

최초 진단에서 document `networkidle`만 기다린 뒤 이동했더니 홈의 남은 요청도 뒤따랐다. 원시 기록은 `baseline-fast-navigation.json`으로 보존했다. SPA에서는 이미 도달했던 document load-state가 다음 화면 데이터 완료를 보장하지 않는다. 그래서 주 표본은 홈의 최종 데이터 카드로 준비 완료를 확인해 다시 측정했다.

빠른 연속 이동 시 불필요한 이전 화면 요청/중복 stats가 남을 수 있다는 별도 관찰이며, 이번 문제의 유일한 원인이라고 하지 않는다. 취소·캐시 정책을 임의로 추가하지 않는다.

## 승인 전 후보 (아직 선택/구현하지 않음)

- 로딩 중 거짓 기본값을 숨기고 명시적 대기 상태/공간을 표현: 표시의 정직성과 재배치 개선, 네트워크 대기 자체는 그대로.
- 독립된 MY 읽기 요청 병렬화: 고지연 누적 감소, 표시 문제는 따로 다뤄야 함. 공개 API 변경 없이 가능하나 오류/이탈 처리 검토 필요.
- 서버 통합 응답 또는 마지막 화면 캐시: 계약/신선도 범위가 커짐. 현재 필요성을 확정하지 않았으며 먼저 만들지 않는다.

조사 후 문제 판단과 해결 방향을 각각 승인받았다. 두 승인 전 제품 코드는 바꾸지 않았으며, 승인 원문과 범위는 승인 기록에 보존한다. 실기기 수정본의 최종 확인은 아직 남아 있다.
